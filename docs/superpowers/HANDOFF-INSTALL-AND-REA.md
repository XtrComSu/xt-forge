# xt-forge installer and REA follow-up handoff

**For the implementing agent.** Make installation and updates predictable on Windows, Linux, and macOS. Start with Windows and verify the installed command from a real Windows shell. Follow the existing [binary workbench roadmap](HANDOFF-BINARY-WORKBENCH.md) for the analysis work. Land installer changes independently so they can be reviewed and released on their own.

## Fix the current installers

1. **Windows launcher and setup.** Start in [install.ps1](../../install.ps1) and [bin/xtforge.cmd](../../bin/xtforge.cmd). The CMD wrapper switches into the source tree in its Python fallback, so a relative path passed from another directory resolves against the wrong directory. It also reads `%ERRORLEVEL%` inside blocks, where expansion can precede the command whose status is needed. Preserve the caller's working directory, return the actual exit status, and validate that the chosen Python is at least 3.11. Exercise the Python launcher fallback on a machine where `python.exe` is a Windows Store alias. Verify the installed command before reporting success or persisting a PATH entry. Update user PATH idempotently and update the current PowerShell process too. Replace the unsafe `setx PATH` advice in the [npm launcher](../../bin/npx-xtforge.mjs), which copies the combined process PATH into the user setting. Verify profiles and install paths with spaces and non-ASCII characters.
2. **Linux and macOS launcher.** [bin/xtforge](../../bin/xtforge) relies on `readlink -f` to find its source from a symlink. I reproduced a failure with a reader that supports plain `readlink` only. The installed alias looked beside itself and failed to import `xtforge.cli`. Resolve relative and absolute symlink chains portably or install a self-locating wrapper. Exercise Apple Silicon Homebrew-only PATH and a fresh shell. Keep the default install per-user and make PATH instructions match the actual destination.
3. **Safe reinstall and useful errors.** Both source bootstrap scripts reset the managed checkout. Replace this with a checked fast-forward or stage a fresh tree; preserve local changes and the last usable install. Stop on failed checkout or install verification and name the failed command. Make Python-only mode explicit. Treat optional native build failures as degraded capability with an actionable reason, and verify that the advertised commands work in that mode. Preserve existing npm, Python, and CLI entry points.
4. **Prefer prebuilt releases for end users.** Audit the archive *contents* against the README and launcher paths before making release archives the default. The local 0.4.6 Windows and macOS archives I inspected did not contain the advertised native executables; the Linux one contained both. Build and validate per-platform artifacts in CI. Start with Windows x64, Linux x64, and macOS arm64; add Windows arm64, Linux arm64, and macOS x64 wherever supported by the release matrix. Verify integrity before activating the install and retain the last working version if an update fails. A native release install should avoid requiring Git, Node, Go, Rust, or build tools. State any Python runtime requirement clearly. Assess a signed Windows installer or WinGet packaging once the archive contract works.

The upstream release listing identifies **rea-agents 6.10.1, published November 20**, as latest. It was the first 6.10 build published to npm and incorporates 6.10.0's features. The 6.9.0 notes add context about standalone containers and bounded, paginated evidence. ## Review gates

- Run the same packaged smoke test on Windows PowerShell 5.1 and 7, Linux, and macOS. Use a standard user and clean environment. Exercise install twice, paths with spaces and Unicode, startup from outside the checkout, CLI aliases, relative file arguments, a deliberately failing command, and an MCP `initialize` plus `tools/list` exchange.
- Test a clean download, optional-component failure, PATH already present, a dirty checkout, a failed update, and a fresh terminal. For Windows, exercise both `python.exe` and launcher-only environments. For macOS, test symlink behavior on the supported runners. Verify install paths from both a source checkout and a release archive.
- Run a representative packaged native analysis on each host. An install smoke test that only checks `--version` can pass without a working hub. Publish OS, CPU, shell, runtime, artifact checksum, and outcomes so the reviewer can distinguish native coverage from Python fallback.
- Use and extend [the shipped-package tests](../../tests/test_shipped_packages.py) and [the cross-format verifier](../../scripts/verify_sys_native.py). Return the diff and run logs for review. Keep the existing 0.4.7 changes intact.
