### Formats

ELF (32/64, symbol versions, `.gnu_debuglink`) · PE (x86, x86-64, arm64, **arm64ec /
arm64x** distinguished, DLLs, export table) · Mach-O (thin + universal, function starts) ·
ar archives · **standalone COFF objects** · **Intel HEX** · **Motorola S-record** ·
**Android boot images** · **Android OTA packages** · **UEFI firmware volumes** · **raw
images with an explicit arch and load address** · any unknown file (bounded description,
see below).

```
$ re overview prog.obj          $ re overview boot.img
format: coff                     format: androidboot
machine: 0x8664 (x86-64)         kernel: 1234  page: 2048
5 sections, no entry point       name: "test"  cmdline: "console=tty"
```

A COFF object is deliberately not runnable: it has sections and symbols, but no entry
point and no functions until it is linked. The Android boot reader inventories the header
only — the kernel and ramdisk are compressed payloads it does not decompress. The UEFI
reader lists volume files and their types but never decompresses a section. An ordinary
ZIP is *not* claimed as an OTA; detection requires `payload.bin` or
`META-INF/com/android/` metadata.

PDB type rendering gained arrays and qualifiers, which required a correction worth
recording: in the MSVC ABI a parameter written `int arr[4]` **decays to a pointer**
(`0x0674`), so the array only appears for `int (*arr)[4]`. The test fixture was extended
with that form and with a `const int *` parameter so the new rendering is actually
observable:

```
0x100c -> int (int[4] *)
0x100e -> int (const int *)
```

```
$ re overview firmware.hex
format: ihex   records: 2  segments: [(0x100, 16)]
$ re overview firmware.srec
format: srec   records: 2  segments: [(0x1000, 16)]  entry set
$ re overview blob.bin --arch arm64 --base 0x80000
format: raw    arch: arm64  bits: 64  section "raw" at 0x80000
```

`--arch` never shadows a real format: `re overview a.exe --arch x86_64 --base 0x140000000`
still reports `format: pe`, because the PE loader understood the file. Raw mode is the
last resort, exactly like the unknown fallback.

Intel HEX and S-record are recognised **after** every binary loader has declined, since
they begin with a character rather than a magic. Both validate checksums, count bad
records instead of aborting, cap expansion at 16 MiB, and never panic on truncated input.

Verifier lanes prove PE x86, PE arm64 EXE, PE arm64 DLL, ELF, Mach-O and arm64 IPA
end-to-end through the packaged CLI and both MCP paths.

### 32-bit ARM: from unmappable to disassemblable

Until this batch, `re disasm-native` refused every 32-bit ARM image — the brief's Stage 2
asks for "ELF and PE on 32-bit x86 and ARM/Thumb", and only the mapping half existed.
There is now an A32 decoder (`internal/sysimage/arm32.go`).

**Verified against `llvm-objdump` instruction for instruction**, not against my own
fixture: a C program with a loop, a switch, struct access, a call and `svc #0` compiles to
**33 instructions**, and the decoder reproduces **33/33** of them — mnemonic *and*
operand text — for a 100% match rate against the oracle. The test fails below 90% and
prints the mismatching pairs, so the number cannot quietly rot.

```
$ re disasm-native prog_arm_linked
push {r11, lr}
sub sp, sp, #8
mov r0, #2
str r0, [sp, #0x4]
```

Two limits found while wiring it up, both now stated in the code and the verifier:

- **A relocatable ARM object cannot be disassembled by address.** Every section sits at
  address 0, so "address 0x0" is genuinely ambiguous and the hub refuses it — correctly.
  The verifier therefore links a freestanding ARM executable (`-nostdlib -fuse-ld=lld
  -Wl,-e,main`) and disassembles its entry: `linked entry 0x20104 decoded 8 instructions
  (0 opaque)`.
- **Thumb now decodes too**, and mode is detected rather than guessed (see below).

### `checksec` on ELF, checked against `readelf`

The Mach-O work raised the obvious question of whether the ELF checks were right. They are,
on both a soft and a hardened build:

| Flag | soft build | hardened (`-fstack-protector-all -z relro,now`) | oracle |
|---|---|---|---|
| nx | true | true | `GNU_STACK` is `RW`, no `E` |
| pie | true | true | `DYN` + `FLAGS_1: PIE` |
| relro | Partial | **Full** | `GNU_RELRO` present; Full requires `BIND_NOW` |
| canary | false | **true** | 0 then 1 `__stack_chk` symbols |

Partial versus Full is the subtle one: `GNU_RELRO` alone is Partial, and Full needs
`BIND_NOW` in the dynamic section. Both cases agree with `readelf`.

| Apparent failure | Actual cause |

### REA through Ghidra, measured against XT-Forge (5 repetitions)

REA was installed far enough to run, and the comparison is now real rather than blocked. The
chain that made it work: `npx rea-agents` needs Node >= 22.23.4 (the system has 22.23.3, one
patch short), and every analysis verb needs a disassembler provider — Ghidra, Hopper, IDA or
Kuna. Ghidra 12.2 was unpacked under `~/.local/providers/ghidra_12.2_PUBLIC`, and it rejects
JDK 21: its readiness check demands **JDK 25**, so Temurin 25 was installed beside it.

```
$ rea analyze <binary> --json          # 5 runs each, median wall time
binary        REA (Ghidra)                    XT-Forge                  (re-run after descent + gap scan)
elf-64        11.56 s   23 fns  74 strings   0.003 s   10 fns
pe-64         25.48 s 3955 fns 3465 strings  0.016 s 2776 fns
pe-32         28.04 s 3530 fns 3672 strings  0.017 s 3538 fns   <- was 1411
macho-arm64   10.10 s    2 fns   8 strings   0.002 s    3 fns
```

**32-bit PE reached parity: 3538 against REA's 3530 — a 0.2% difference on the same binary.**
Two increments produced it: recursive descent from exports/entry (1411 → 2148) and the
tightened gap scan (2148 → 3538). Both are measured above; neither was tuned to the number,
and the density check (55.6 B/fn vs Ghidra's 56) is what says the agreement is structural
rather than a coincidence of totals.

Raw run: `docs/superpowers/bench-rea-vs-xtforge-2026-11-23.json`.

**What both agree on:** format and architecture match on all four binaries (the one apparent
mismatch was spelling — REA says `mach-o`, XT-Forge says `macho`).

**Correction: the function-count gap is not a recall gap.** REA reports **3955** procedures on
64-bit Kernel32 where XT-Forge reports **2776**, and I first read that as us missing 42%. It is
not. A 64-bit PE declares its non-leaf functions in `.pdata` — one `RUNTIME_FUNCTION` each —
which is the strongest ground truth that exists for this question, and XT-Forge already indexes
**100% of them**:

```
kernel32.dll    1870 .pdata entries   2776 indexed   0 missing
kernelbase.dll  2915 .pdata entries   3014 indexed   0 missing
ucrtbase.dll    4545 .pdata entries   4553 indexed   0 missing
```

`TestPEDataCoversEveryDeclaredFunction` pins the invariant. Both tools exceed `.pdata` with
candidates no directory attests to — leaf functions, thunks, analysis artefacts — so a raw
count difference says nothing about coverage. Establishing which tool's extra entries are real
would need REA's per-address list, which its `analyze` payload does not carry.

**Where XT-Forge wins, by three orders of magnitude:** speed. 0.002–0.016 s against 10–29 s,
because Ghidra pays a JVM plus headless-analysis startup on every invocation. For an agent
that must answer dozens of questions per turn, that difference decides feasibility.

**Correction: the "segments" row was a category error, not a product gap.** REA reports 34 for
`/tmp/dy`; inspection shows those are **Ghidra memory blocks named after ELF sections**
(`.dynsym`, `.interp`, `.gnu.hash`, … plus synthetic `segment_2.x` blocks). XT-Forge's
`segments` are the **4 loadable `PT_LOAD` program headers**, because that list exists to answer
"which file bytes map to which address" — the other 11 program headers (`PT_INTERP`,
`PT_DYNAMIC`, `PT_GNU_EH_FRAME`, `PT_GNU_STACK`, `PT_NOTE`, `PT_GNU_RELRO`, …) carry no file
mapping and are correctly excluded. `re info` reports all **15** program headers alongside 31
sections. Comparing 34 with 4 measured two different things; the row is now labelled
`segments_ghidra_blocks` rather than silently scoring it. And four of the fifteen tiers are all this covers — decode, xrefs,
decompilation and dispatch need a provider call per address in REA, which would mean hundreds
of Ghidra sessions, so they are **not** compared rather than quietly scored.

### ARM32/Thumb now lift into typed IR

Both architectures could be disassembled and neither could be decompiled: `lift.go` returned an
opaque operation per instruction, so `re decompile-native` produced nothing usable for the
architectures most common on Android ARM32 firmware.

`lift_arm32.go` maps the A32 and Thumb subsets onto the **existing** IR vocabulary — `copy`,
`copy_pair`, `add`, `sub`, `and`, `or`, `xor`, `shl`, `shr`, `sar`, `flags`, `call`, `jump`,
`branch`, `return`, `nop`, `trap`, `address` — rather than inventing opcodes the structured
analyser would not recognise. Measured on a real A32 binary: **11 of 11 decoded instructions
lift, 0 opaque**; the Thumb fixture is 8 of 8.

The output is now typed operations instead of opaque text:

```
parallel_copy(mem32[sp + -8], mem32[sp + -4], r11, lr); sp = sp - 8
sp = sub32(sp, 0x8)
r0 = 0x2
mem32[sp + 4] = r0
```

**AAPCS32 landed after this**, so the calling convention is no longer the blocker:
`aapcs32_integer` (r0–r3 arguments, r0 result, r4–r11 saved) was added and a simple function now
emits real C:

```c
static uint32_t sys_callee_200f4(uint32_t arg0, uint32_t arg1) {
    return (arg1 + arg0);
}
```

**A real compiled binary still declines, and the two reasons are specific:**

1. `arm: unsupported operation "sub"` — **partly fixed this round.** The ARM32 stack-adjust
   path fed ARM's `#`-prefixed immediate text ("#0x8") straight to `strconv.ParseUint`, which
   rejects it, so every function whose first act is a stack adjustment declined. Stripping the
   prefix moved the decline past that site on both fixtures (0x20106 → 0x20184, 0x20152) and is
   pinned by `TestARM32StackAdjustAcceptsImmediatePrefix`. **It still declines later**, and the
   next round narrowed it further: the lifted IR for that site is already correct —

   ```json
   {"opcode":"sub","destination":{"register":"sp","width":32},
    "inputs":[{"register":"sp","width":32},{"immediate":"0x8","width":32}]}
   ```

   — so the lifter was not at fault. **The cause was found and fixed:** a Thumb prologue's
   `sub sp, #8` runs before `sp` has been marked as stack, so `inputs[0].stack` was false, the
   ARM32 stack branch was skipped, and the write to `sp` failed downstream as an unsupported
   operation. The analysis now treats the stack register itself as offset zero.

   With that fixed the decline moved to the next real obstacle, and the next round located it
   with one instrumented run: **a call to a `void` function is rejected.**

   ```
   DBG call: target=0x2014c value empty; sp.stack=true sp.off=-8 home=0 arch=arm
   ```

   The target is `trap`, which is `svc #0`. Reading the resolver corrects the first reading of
   this: a *void* callee is not the problem, because `callValue` returns the call expression
   (`"trap()"`) with width 0, and that text is not empty. Empty means the callee's summary is
   **nil** — `newCalleeResolver` re-analyses the callee, `trap`'s own analysis declines (it is a
   `svc` stub with no modelled behaviour), and the caller then treats an unresolvable callee as a
   failure of its own.

   One more layer down, and this is the accurate one: **the walk has no `trap` case.** `svc` is
   lifted to opcode `trap`, `apply`'s switch does not handle it, so `trap`'s own analysis returns
   nil — and its caller then declines. Note that `svc` *does return*; modelling it as noreturn
   would be wrong, and so was my first framing of this.

   **Fixed:** the walk now has a `trap` case that ends the body without claiming a return value,
   so a `svc` stub summarises as a void callee. The decision it needed was made explicitly rather
   than by accident — the encoding does not say whether the supervisor call returns or exits, so
   the analysis claims neither a value nor a terminator it cannot justify.

   With that in place the decline moved one callee further, which is exactly the shape of progress
   on this thread:

   ```
   before:  target=0x2014c (trap)  calleeNil=true
   after:   target=0x20136 (use)   calleeNil=true
   ```

   `use` is `sum(&p->a, 2) + pick(p->b)`, a callee with **pointer** parameters — but the trap work
   also exposed a second, smaller gap that a new test pins:

   ```
   stub declined=""                                  <- the svc stub summarises
   caller declined="arm: call could not be summarised under the calling convention"
   ```

   A caller whose **only** callee is that summarised void stub still declines. So the direct path
   and the resolver path disagree: `Decompile` at the stub succeeds, while `newCalleeResolver` —
   which re-analyses the callee from its own entry — still produces nil for it. That is the
   narrowest remaining item on this thread and the first thing to look at next, before the
   pointer-parameter question. `TestTrapStubSummarisesAsVoidCallee` records both strings.

   **Resolved to a concrete cause.** The resolver discarded the callee's decline reason, which is
   why this looked mysterious; one instrumented run printed it:

   ```
   DBG resolve 0x20136 reason: "unsupported operation \"opaque\" at 0x20136"
   ```

   The opaque operation is `push {r4, r5, r7, lr}` — a **four-register push**. The ARM32 lifter
   deliberately leaves push/pop lists wider than two registers opaque (it has no `parallel_copy`
   lowering for N registers), so `use` cannot be summarised, so its caller declines. The chain
   terminates in a documented lifter limitation, not in the analyser and not in ARM32 plumbing.

   **The fix is blocked by an IR limit, not by the lifter.** `Operation` has exactly two
   destinations (`Destination`, `SecondDestination`), and `copy_pair` is a two-destination form.
   A four-register push therefore cannot be expressed faithfully as one operation, which is why
   `liftARM32StackList` refuses lists wider than two rather than dropping registers silently.

   Two ways forward, both real design decisions rather than patches:

   1. **Extend the IR** to carry N destinations (`Destinations []Operand`), and teach
      `apply`/`renderSummary` about it. Faithful, and it would serve other architectures' wide
      loads too, but it touches the IR contract every lifter and the analyser share.
   2. **Add a `stack_list` opcode** meaning "move sp by 4·N and clobber these registers", which
      is all the analyser needs in order to continue past a prologue. Smaller, less faithful, and
      it deliberately does not model the individual slot writes.

   **Option 2 was implemented.** `push`/`pop` with more than two registers now lift to
   `stack_push_list`/`stack_pop_list`, which the analyser applies as "move sp by 4·N and treat
   those registers as clobbered". The individual slot writes are deliberately not claimed. With it,
   `trap`'s caller `use` no longer stops at its prologue, and the next blocks are a different kind:

   ```
   sum   (0x20104): the function could not be summarised as a single expression   <- a loop
   pick  (0x20122): disassembly reported warnings: decode at 0x20124              <- a Thumb decode gap
   ```

   The undecoded instruction at `0x20124` was a 32-bit Thumb-2 `MUL` (`fb00 f201`), now decoded and
   rendering exactly as llvm-objdump does (`mul r2, r0, r1`). The next one is a different kind:

   ```
   0x2012c: bf38  it lo
   0x2012e: f102 010b  addlo.w r1, r2, #0xb
   ```

   An **`it` (If-Then) block**. Decoding it properly needs state carried across the following one
   to four instructions, because `it` supplies their condition — that is a decoder state machine,
   not another case in the switch. So the ARM32 structured picture is now limited by
   **loop summarisation** and **IT-block state**, both named and neither a prologue problem. Two diagnostics worth keeping regardless: `newCalleeResolver` should not discard the
   decline reason (dropping it turned a one-line cause into six rounds of hypotheses), and that
   reason belongs in the caller's `structured_declined` text.
2. `unsupported ARM32 instruction word 0xe7913102` — a register-offset load with an `LSL`
   scale (`ldr r3, [r1, r2, lsl #2]`) is not decoded at all.

Both are small and precisely located. Neither is claimed as working.

Deliberately left opaque instead of being given a wrong opcode: register-form `mvn`/`bic`
complements, carry arithmetic (`adc`/`sbc`/`rsc`), register lists wider than two registers in
`push`/`pop`, and register-offset memory with `lsr`/`asr`/`ror` scaling.

### 32-bit PE: recursive descent landed, gap scan rejected

32-bit PE has no `.pdata`, so nothing attests which addresses are functions. Two increments
were built and measured separately.

**Landed — recursive descent** (`pe_descent.go`). Seed from every indexed function, the entry
point and `.pdata`, then decode and treat every direct `E8` call target as a function start.
Bounded, deterministic, never overwrites a name:

```
i386 kernel32.dll   1411 -> 2148   (737 added, 48.8 ms)   all 1414 exports still indexed
x86-64 kernel32    2776 -> 2776    (0 added — .pdata coverage is already 100%)
```

The whole 1 600-binary corpus still parses with 0 failures (400 files in 1.6 s per directory).

**Rejected, then rewritten and landed — linear gap scan.** The first version accepted any
plausible prologue in uncovered bytes. It worked, and it overshot:

| binary | our count | bytes per function | verdict |
|---|---|---|---|
| kernel32 i386 | 1411 before | 139 | too sparse |
| kernel32 i386 | 5731 with gap scan | **34** | implausible — dense beyond real code |
| kernel32 i386 | REA 3530 | 56 | plausible |
| advapi32 i386 | 1008 before | 146 | too sparse |
| advapi32 i386 | 2901 with gap scan | **51** | implausible |
| advapi32 i386 | REA 1543 | 96 | plausible |

A prologue alone is not evidence of a function start: `push ebp` occurs inside function bodies
too. Merging that version would have doubled the index with entries nothing attests to — the
failure mode a count-based benchmark rewards and a user pays for.

**The tightened version landed, then the coverage model changed under it.** `functionExtent`
decodes each known start until a terminator and attributes only that body, instead of assuming
everything up to the next start belongs to the function. Kernel32 and advapi32 stayed within a
byte of Ghidra's density; activeds tightened from 190 to 193 B/fn (Ghidra 155); **aclui did not
move**.

**aclui is a measured miss, not a silent pass.** Its `.text` packs functions with no alignment
padding: 163 positions pass the prologue test, 23 pass the predecessor-byte test, 20 pass the
six-instruction test. With 5 pre-existing starts, accepting *every* rule-D candidate still caps
it at 25 functions (~328 B/fn), so the 90..200 band is unreachable without relaxing rules C and
D. Loosening rule C for every image to fix one 8 KB DLL would undo the precision the previous
round established, so it stays a documented miss with a non-regression assertion instead.

**The earlier tightened version**, with five acceptance rules (strict prologue, a padding/`ret`
byte before it, six clean instructions reaching a terminator, 8-byte spacing, region bounds):

| binary | before | after | bytes/fn before → after | Ghidra |
|---|---|---|---|---|
| kernel32 i386 | 2148 | **3465** | 139 → **56.7** | 56 (3530 fns) |
| advapi32 i386 | 1008 | **1608** | 156 → **95.4** | 96 (1543 fns) |
| activeds i386 | 52 | **127** | 473 → **193.5** | 155 |
| aclui i386 | 6 | **23** | 1638 → **372.4** | 120 |

The numbers moved slightly when the coverage model changed from "start .. next start" to
"decoded body of each function": attributing only a real body to a known start exposes the
bytes after it, which is what the packed small DLLs needed. It also means the earlier 3538 was
partly the previous model's artifact; 3465 is the same code measured honestly.

On the two large DLLs the density now lands within a few percent of Ghidra's
(55.6 vs 56, 89.2 vs 96) — independent agreement on *where the code is*, not just how much.
The two small DLLs stay sparse: the rules under-discover there, which the test states rather
than hides.

The band in the test is 45..140 bytes per function, not the 60..140 I first wrote. Ghidra
itself reports 56 on i386 kernel32, so the original band would have rejected a density that
matches the only credible reference available. **The number I invented was wrong; the
measurement corrected it.**

### PDB types: `double` rendered as `type(0x0041)`, `short*` as `type(0x0611)`

The PDB type table was deliberately small — "only entries verified against llvm-pdbutil are
listed" — but it was missing most of the common types, so a `double` field printed as
`type(0x0041)` and every pointer printed as a raw index. Both were measured against
`llvm-pdbutil dump -types`, which names 0x0041 "double" and 0x0611 "short*":

```
struct Rec /* 16 bytes */ { int a; type(0x0041) b }
struct Rec /* 16 bytes */ { int a; double b }
```

Two additions, both oracle-derived:

- **The simple-type table** now covers the signed, unsigned and real-number families
  (0x10-0x13, 0x20-0x23, 0x30, 0x40, 0x41, 0x70, 0x74, 0x75) with their widths.

### Parameter names: `int takes_array(int*, unsigned long, struct Rec *)`

A signature knows the argument *types* and never their names, so a caller reading
`int*, unsigned long, struct Rec *` cannot tell which is the buffer, which is the count and
which is the record. The names live in the symbol stream as `S_LOCAL` records flagged
`param`, inside each `S_GPROC32` scope:

```
  args:  ['int*', 'unsigned long', 'struct Rec *']
  named: [('values', 'int*'), ('count', 'unsigned long'), ('r', 'struct Rec *')]
```

The join is on the procedure's type index, which both streams carry.

**The offsets had to be body-relative.** My first version used the record-absolute values
(4/8/10) against a body that already skipped `reclen` and `rectyp`, putting the walk two
bytes late. It produced a parameter named `t` with type index `0x6f630001` — a wrong answer
that still looked like a name and an index, which is why the test now rejects any type index
above `0xFFFF` (a real one is a small number; a misread string is not).

Raw bytes of a real `S_LOCAL`, for the next reader:

```
3e 11 | 74 06 00 00 | 01 00 | values
rectyp  type int*     param   name
```

### Array dimensions: `int grid[2][3]` rendered as `int[3][]`

Both dimensions were wrong, in two different ways.

**The count was missing** because it needs the *element's* width, and the element is often
not a simple type: a nested array, a struct, or a pointer. `pdbTypeWidth` now recurses
through arrays, structures, pointers and modifiers, and returns 0 when it cannot tell —
callers then omit the count rather than inventing one.

**The order was reversed** because the renderer appended the current dimension *after*
recursing into the element. Dimensions are now collected outermost-first, which is how C
declares them.

**One case needed the forward-reference chain.** `struct Rec list[2]` still printed `[]`
until the record was inspected: `0x1006` is an `LF_STRUCTURE` with `options: forward ref
(-> 0x100C), sizeof 0`. The real definition lives elsewhere in the stream, so the width is
now resolved by matching the definition's name.

```
before:  { int[3][] grid; struct Rec[] list; char*[] names }
after:   { int[2][3] grid; struct Rec[2] list; char*[4] names }
```

Every count matches the oracle's own arithmetic (24/12, 32/16, 32/8), and the rendering
matches the C source declaration order.

### A regression test that does not fail on its bug is not a test

After fixing the 2^32 error I wrote `tests/test_re_reference_targets.py` to compare every
reference target with `llvm-objdump`'s annotation. Then I checked whether it would actually
have caught the bug — reintroduced it, ran the test, and it **passed**.

The reason was mundane and worth writing down: the test drives the CLI, which runs a

```

    reference targets disagree with llvm-objdump: 0x10a8 want 0x1070 got ['0x100001070']
```

Any regression test for a compiled component has to be run against a binary built *from the
broken source*, or it proves nothing. This one now does, and the two-fixture pair
(`test_backwards_and_forwards_both_resolve`) stops a future "fix" that simply negates every
displacement.

### Every backwards memory reference was wrong by 2^32

Wiring `ClassifyAddress` into cross-references (it existed, was tested, and was called by
nothing) immediately produced a target classified `unknown` at `0x100001070`. The address
was inside a small binary, so it was worth looking at:

```
llvm-objdump:  10a8: leaq -0x3f(%rip), %rdi   # 0x1070 <main>
ours before:   target 0x100001070  class unknown  name -
ours after:    target 0x1070       class code     name main
```

The cause: the vendored decoder reports `x86asm.Mem.Disp` **unsigned**. A RIP-relative
displacement is a signed 32-bit field, so `-0x3f` arrived as `4294967233`, and adding it to
the instruction end gave `0x100001070`. **Every backwards memory reference in a 64-bit binary
was off by 2^32** — string loads, GOT slot reads, and any access to data placed before the
instruction.

`x86asm.Rel` is already signed, which is why branch targets were correct and only memory
operands suffered; that asymmetry is why the bug survived so long without a symptom that
looked like an addressing error.

The fix sign-extends the displacement only for RIP-relative operands, leaving absolute
addressing alone. `TestRIPRelativeNegativeDisplacement` pins backwards, forwards and
zero displacements against `llvm-objdump`'s own answers.

### `dispatch-native` only ever looked at `_start`

Without `--target`, dispatch analysed the **entry point** and reported `tables: 0`. For a
normal executable that is CRT glue, so the answer read as "this binary has no jump tables"
while the binary's own switches had never been examined. The result did name the function it
used, but nobody reads `function: 0x1020 _start` and concludes anything useful.

It now sweeps the function index when no target is given, bounded to 4096 functions and 512
tables:

| fixture | before | after |
|---|---|---|
| dense switch (8 cases) | 0 tables | **1 table**, `bound 7`, `entries 8`, `fn: dense` |
| sparse switch (8 cases) | 0 tables | **2 tables** |
| 81 MB binary | 0 tables | 4096 functions scanned in **4 s** |

Each table now carries the function it belongs to, which only matters once a single call can
return tables from more than one function.

Honest limit: the sweep takes the first 4096 functions by address, so on a very large binary
it examines an unrepresentative slice and can still report few or no tables. That is bounded
work rather than full coverage, and the count of scanned functions is in the output so the
difference is visible.

### `re rtti` reported 7 classes for a 2-class binary

Before extending `rtti` to another format I ran it on a fixture that genuinely needs RTTI
(`typeid` plus `dynamic_cast`, so the optimiser cannot drop it). It found the classes
correctly — complete with vtable method previews showing the overridden body — and then

```
before:  7 classes   Base, Derived, _ZTVN10__cxxabiv117__class_type_infoE,
                     _ZTVN10__cxxabiv120__si_class_type_infoE,
                     _ZTVN10__cxxabiv117__class_type_infoE@CXXABI_1.3, …

```

Four kinds of noise, each with a different cause:

- the **C++ ABI's own vtables** (`__cxxabiv1`) are implementation plumbing, not user classes;
- **versioned aliases** (`…@CXXABI_1.3`) duplicate a symbol already counted;
- **undefined imports** carry value 0 and describe nothing here;
- `_ZTV7Derived` and `Derived` are the **same class** under a mangled and a demangled name,
  so comparing raw strings let it through twice.

The last one needed `_vtable_symbol_class`, which reads the Itanium length-prefixed name and
deliberately gives up on nested (`N…E`) and templated names rather than guessing — merging
two unrelated classes would be worse than listing one twice.

A stripped build of the same fixture still yields `Base` and `Derived`, from the structure
scan rather than symbols, so the fix improves the symbol path without weakening the other.

### `checksec` now answers for Mach-O — and three of its checks were wrong

`re checksec` was ELF/PE only, which meant the platform where hardening questions matter
most (iOS/macOS) got a format complaint. Mach-O hardening is now read from the header flags
and the undefined symbol table: PIE, NX stack, NX heap, two-level namespace, code signature,
encryption, stack canary, ARC and `_chk` fortification.

```
$ re checksec "Delta Installer" --arch arm64
pie: true  nx_stack: true  canary: true  arc: true  code_signed: true  imports: 583
```

That 583 matches `llvm-nm -u --arch=arm64` exactly. Without `--arch` the first slice is used
(x86_64, 601 imports) and the result says which slice it examined.

**Two bugs, both found by checking against an oracle rather than reading my own output:**

- **`MH_ALLOW_STACK_EXECUTION` was written as `0x10000`.** That value is
  **`MH_BINDS_TO_WEAK`**; the real flag is `0x20000`. The effect was a hardened iOS app
  reporting `nx_stack: false` — a wrong answer to a security question, in the direction that
  matters. `llvm-objdump` printing `BINDS_TO_WEAK` for the same header word is what exposed
  it.
- **Undefined-symbol detection checked `N_EXT` but not `N_TYPE`.** Every *defined* symbol was
  counted as an import, so a freestanding binary reported three imports where it has none.
  `llvm-nm -u` printed nothing, which is how the disagreement surfaced.

- **The dylib count was counting a *set*.** `command_set` collapses duplicate command
  types, so a real iOS app with 13 `LC_LOAD_DYLIB` plus 14 `LC_LOAD_WEAK_DYLIB` reported
  `dylibs: 2`. It now counts occurrences in the command list: 27, matching the load
  commands. The test uses a synthetic image with three dylib commands, because there is no
  iOS SDK on this machine to link against.

Three bugs in one module, all from writing constants and counts from memory rather than
from the file. After the first two I cross-checked every remaining constant that drives a
decision — `LC_CODE_SIGNATURE`, `LC_LOAD_DYLIB`, `LC_SYMTAB`, `LC_BUILD_VERSION`,
`MH_TWOLEVEL`, `MH_PIE` — against `llvm-objdump`'s own listing, and those are correct; the
error was only in the value I had *made up*, not the ones read off a spec.

All three are pinned in `tests/test_re_macho_checksec.py`, including a direct count comparison
against `llvm-nm -u`.

### The structural fix: `xtforge/core/re/sources.py`

Four verbs had been patched one at a time — `sections`, `needed`, `symbols`, `info` — each
growing its own hub fallback. Four identical fixes is the signal that the decision belonged
somewhere shared, so it now does:

```
sources.hub_overview(path)        the engine's view, or None
sources.hub_format(path)          "elf" / "pe" / "macho" / "unknown" / ...
sources.sections_from_hub(path)   rows, or None
sources.needed_from_hub(path)     de-duplicated list, or None
sources.named_functions_from_hub(path)   named functions (not a symbol table)
sources.info_from_hub(path)       header metadata, including container archives
sources.unsupported(verb, path)   a refusal that names what does work
```

The rule is written down once: **a format-specific Python reader wins where one exists**,
because it reports more detail than the generic view (`re symbols` on ELF: 41 entries from
the Python reader vs 12 named functions from the engine); otherwise the engine answers.

Live check, same two files, all four verbs:

| | Mach-O (universal) | ELF |
|---|---|---|
| info | ok, hub | ok, python |
| sections | 40, hub | 31, python |
| needed | 13, hub | 1, python |
| symbols | 12, hub | 41, python |

`tests/test_re_sources.py` pins the dispatcher directly, so a verb built on it cannot drift
away from its siblings again.

Two of my *expectations* were wrong while writing those tests, and both are worth recording
because the code was right:

- the format string is `"macho"`, not `"mach-o"`;
- an unrecognised file is **not** a failure — the engine returns `ok: true` with
  `format: "unknown"` plus a hash, entropy and a bounded preview. The dispatcher passes that
  through, and the test now asserts it rather than assuming `None`.

### `re info` was the fourth verb with the same shape

`info` answered for ELF and PE and nothing else, so a Mach-O or an archive fell through to
"unrecognized binary format" while `overview` parsed the same file without complaint. It now
falls back to the engine:

```
Delta Installer (Mach-O)  ok: true  machine: x86_64  class: 64-bit  engine: xtforge-hub
liba.a (archive)          ok: true  members: 1  member_names: ["a.o"]
libc-backed ELF           ok: true  engine: python     (unchanged, richer detail)
```

One shape assumption cost a cycle: the hub reports an archive as a **plain member list**,
not `{"members": [...]}`, so the first version of the fallback returned `ok: false` for a file
the engine had just parsed correctly. The test for it asserts the member list, which is what
made the difference visible.

Remaining ELF/PE-only verbs, recorded rather than silently failing: `checksec` (needs
hardening-flag logic per format) and `rtti` (needs C++ RTTI scanning per format). Both now
report the format honestly instead of implying the file is unreadable. `entropy`, `pack` and
`ioc` already work on any bytes.

### All three listing verbs, not just `sections`

Asking "do two verbs reading the same file agree?" found the same defect three times:

| Verb | Before | Now |
|---|---|---|
| `sections` | Mach-O: nothing | 40 sections via the hub |
| `needed` | Mach-O: `"not an ELF file"` | 13 dylibs, de-duplicated across slices |
| `symbols` | Mach-O: `"unrecognized binary format"` | 12 named functions, labelled as such |

Two details matter more than the fixes:

- **De-duplication.** A universal binary repeats the same dependencies in every slice, so the
  first fallback returned 26 entries where there are 13. First-seen order is preserved.
- **"Nothing" is an answer.** A freestanding Mach-O linked with `-nostdlib` genuinely needs
  no dylibs, so `needed` returns `ok: true` with an empty list. Answering `"not an ELF file"`
  to "what does this need" is simply wrong when the file is a perfectly good Mach-O that
  needs nothing. My own test asserted the wrong thing here first — it assumed a linked
  binary must have dependencies.

The `symbols` fallback carries a `note` field saying it lists *named functions recovered by
the engine, not a symbol-table listing*, because a client could otherwise mistake 12 entries
for a full symbol dump. When the engine finds nothing named, the refusal names the formats
that are supported instead of saying "unrecognized".

### `re sections` covered two formats out of six

`re sections` returned an empty failure for a Mach-O while `re overview` listed **40
sections** from the same file — because `get_sections` had branches for ELF and PE only.
Format coverage should not depend on which layer answers, so anything the native hub can
read now falls back to it: Mach-O, and COFF objects, dyld caches and kernelcaches along
with it.

```
$ re sections "Delta Installer"     # before: ok=false, no sections
mach-o sections: 40  engine: xtforge-hub  first: __TEXT,__text
```

**The failure also had no message a client could read.** `native.py` reports failures as
`{"ok": false, "err": ...}` — 19 sites — while the rest of the CLI uses `error`. A client
checking `error` saw `ok: false` with nothing else. Rather than rewrite nineteen call sites
and risk breaking consumers, the CLI now emits both keys when a failure uses `err`
(`_normalise_failure` in `cli/common.py`).

An automated flag audit (run each verb with and without a flag, diff the JSON) found two
more inert combinations: `sections --limit` and `entropy --limit` (entropy takes `--count`).
Both are documented as accepted-but-unused rather than fixed here, because truncating a
fixed table is not obviously desirable and `entropy` has its own flag.

### `--confirm` on patch: a flag that could never mean anything

Static audit first: all 181 CLI flags are read *somewhere*. That is why a per-flag grep is
not enough — `--grep` was read by `asar` and ignored by `strings`, and `--confirm` is read by
`trace` and was ignored by `patch`. The question is not "is this flag used" but "does this
verb honour it".

`re patch --confirm yes` did nothing, because `apply_patch` **never writes in place**: it
always emits a copy (`*-patch`, or `--out`). So the flag had no possible meaning, and a user
who passed it would reasonably believe the original had been modified when it had not.

It is now refused with an explanation rather than ignored:

```
error: patch never modifies the input; it writes a copy. Use --out to choose the
       destination instead of --confirm
```

Verified and pinned in `tests/test_re_flag_honesty.py`, along with the two safety properties
that make copy-only patching trustworthy: the input file is byte-identical after a patch, and
`--orig-bytes` refuses on mismatch (`error: original byte mismatch at 0x1130: expected
deadbeef, found 50e8eaff`).

Also checked in this pass and **not** broken: `re annotate export --format json|r2|ghidra`
produces the right output for all three (`afn myb @ 0x1130`, `rename(0x1130, "myb")`).

### Two more presentation bugs: `--grep` and the MCP schema

Continuing the audit of layers *above* the analysis:

- **`re strings --grep X` returned everything.** The flag was parsed and ignored by all
  three modes (plain, `--stack`, `--xor`), so a filtered request produced the full list.
  `--grep warn` now returns 2 matches where it returned 79.
- **The MCP `re_inspect` schema hid the newest verbs.** The dispatcher forwards an arbitrary
  `verb` — `callgraph`, `pdb-types` and `demangle` all worked when called by hand — but the
  published enum stopped at `ioc`. A client reading the schema would never discover them.
  The enum now lists `callgraph`, `demangle`, `pdb`, `pdb-types`, `evidence`, `archives`,
  `kernelcache`, `llvm` and `xrefs`, with argument mapping for the ones that take options.

`tests/test_mcp_re_verb_parity.py` compares the advertised enum against the CLI's own verb
list, so a future verb cannot be added without a route. Four exemptions are explicit and
justified: `borer`, `ida` and `cfg` have dedicated MCP tools, and `pe` is reached through
the `pe_*` verbs.

Two things I checked and did **not** find broken, which is worth recording because both
looked suspicious: `--limit` is honoured by `symbols` and `needed`, and `evidence` does
reach MCP — its record simply has no `ok` key, which my first probe misread as failure.

### Annotations worked; the flags did not

Analyst annotations were implemented and persisted correctly, but two CLI traps made them
look broken:

- **`--target` was silently ignored.** `re annotate <path> --target 0x1130 --name x` stored
  the name at **0x0**, because the command read `--rva` while every other RE verb calls an
  address `--target`. Nothing errored; the name simply never appeared. `--target` is now
  accepted, with an explicit `--rva` still taking precedence.
- **`--name` with no subverb wrote nothing.** It fell through to "list", reported
  `count: 0`, and exited 0. Supplying `--name`, `--comment` or `--type-decl` now infers
  `rename`, `comment` or `type` respectively.

Verified end to end — a rename now shows up in both surfaces:

```
$ re annotate /tmp/xr --target 0x1130 --name my_b
$ re functions /tmp/xr
0x1130   my_b   10B  annotation
$ re disasm-native /tmp/xr --target 0x1130
name: my_b   source: annotation
```

`tests/test_re_annotate_cli.py` pins all three behaviours, including that a bare
`re annotate` still lists.

### String literals at call sites, and the NOBITS bug it exposed

A reference into read-only data is almost always a string literal, and the literal is worth
far more than the address:

```
0x105d -> 'warn: %s\n'
0x1192 -> 'value=%d\n'
0x107b -> 'careful'
```

**The first version reported a `.bss` reference as `"GCC: (GNU) 16.2.1"`.** The target
address was correct — `0x4020`, which `llvm-objdump` agrees with — but the mapping was not.
`.bss` is `SHT_NOBITS`: it occupies memory and has **no bytes in the file**, yet
`elf.Section.FileSize` reports its size. Address-to-file mapping therefore treated `.bss` as
file-backed and read whatever happened to sit at that offset, which was `.comment`.

That is a correctness bug well beyond strings: any address inside `.bss` could resolve to
unrelated file bytes. `elfImage` now zeroes `FileSize` for `SHT_NOBITS` sections, matching
what the Mach-O path already did for zerofill sections, and
`TestNOBITSSectionHasNoFileBytes` pins it.

Two smaller corrections while wiring the feature: a string containing `\n` was rejected as
non-printable (so `"warn: %s\n"` was skipped entirely — tab/newline/CR are now accepted and
escaped for a single-line report), and the `.bss` bug above.

### Imported calls finally have names

On a dynamically linked binary every call into libc went through a GOT slot, and the engine
counted them as anonymous `indirect_calls`. That is the single most useful thing an analyst
wants at a call site, and it was missing.

ELF relocations are the answer: a `R_X86_64_GLOB_DAT` / `JUMP_SLOT` entry names the symbol
and the slot that holds its address, so slot → name is exact rather than guessed.

```
$ re overview /tmp/xr
__libc_start_main   0x3fc0  GLOB_DAT  libc.so.6
__gmon_start__      0x3fd0  GLOB_DAT  -
__cxa_finalize      0x3fe0  GLOB_DAT  libc.so.6

$ re xrefs-native /usr/bin/opencode ...
0x1a4107c -> memcpy
0x1a428db -> memset
0x1a42359 -> environ
```

406 imports resolved on the 81 MB binary, and 73 of the first 2000 references are now
annotated with the import they reach. Cross-checked against `llvm-readelf --relocs`: 7 of 7
matched on the fixture.

**Our output was more accurate than objdump's here.** For slot `0x68522a0` objdump printed
`<writev+0x68522a0>` — it could not name the target — while the relocation table says
`memcpy@GLIBC_2.14`, which is what we report. Worth noting because it is a case where the
oracle is the weaker source, and the right response was to check `readelf` before assuming
our map was wrong.

Support covers x86-64, AArch64, ARM and x86, in both RELA and REL forms.

### A decoder panic, found only by scanning further

Raising the cross-reference cap let a full scan of the 81 MB binary run for the first
time, and it **crashed the process**:

```
panic: runtime error: index out of range [4] with length 4
  x86asm.decodeAVX(...)
```

The vendored `x86asm` indexes `inst.Prefix` past its length on a truncated EVEX (`0x62`)
prefix. One bad four-byte sequence in 81 MB was enough to lose the entire analysis — the
tool died before printing anything.

Two layers of fix, because they answer different questions:

1. **The root cause is repaired.** `decodeAVX` consumed a VEX/EVEX prefix and then read
   `src[pos]` without checking that an opcode byte followed, so a buffer ending exactly at
   the prefix (four bytes: `62 71 FD 48`) indexed past the end. The vendored file now
   returns `truncated prefix`. Its guard is `pos+3 < len(src)`, which lets a *complete*
   four-byte EVEX prefix through and leaves nothing to read.
2. **A recover guard remains.** `safeX86Decode` converts any *other* panic in that decoder
   into a decode error naming the bytes, because a vendored parser is not a place to
   assume only one bug:

```
decode at 0x1000: x86 decoder panic on 6271fd48: runtime error: index out of range [4] with length 4
```

Tests: `TestSafeX86DecodeNeverPanics` sweeps every one- and two-byte prefix (65,792
inputs); `TestVendoredAVXPrefixIsRepaired` calls the vendored decoder **directly** so the
source fix fails loudly if it is ever lost in a re-vendor; and
`TestDisassemblyReportsRatherThanCrashes` pins the public error path. This is the one class
of bug that must never reach a user, because it costs the whole run rather than one
instruction.

The same cap change made full coverage reachable: `maxReferenceFunctions` was 4096, so a
50,670-function binary could never be cross-referenced beyond 8%. It is now 200,000, and a
complete scan of that binary takes **12 s** for 486,463 references across 50,670 functions.

### Large stripped x86-64 binaries: 680 → 50,670 functions

`/usr/bin/opencode` has 81.7 MB of executable code, no `.eh_frame`, and a 26 KB `.symtab`
holding almost nothing useful. The engine recovered **680** functions from it — 1 per
120 KB of code, which is not an analysis, it is an anecdote.

A call-target scan now covers exactly that shape of binary: `E8 rel32` targets, in-range
only, deduped, with the same 4-byte adjacency rule as ARM64.

| | functions | wall time |
|---|---|---|
| before | 680 | ~72 ms |
| after | **50,670** | ~180 ms |

**Quality, measured rather than assumed:** 82.6% of the recovered addresses begin with a
recognisable x86-64 prologue (`endbr64`, `push rbp`, `push rbx/r12–r15`, `sub rsp`,
`mov rbp, rsp`), sampled across 2000 entries. The raw candidate set was 72.3%
prologue-like; dedupe and the adjacency rule improve it.

**It only runs when recovery is sparse** — fewer than one function per 4 KiB of executable
code. Verified both ways: `/usr/lib/libgfortran.so.5.0.0` stays at 2529 functions (it has
`.eh_frame`, so nothing is added), and a normal `-O1` binary gains 0.

**A wall this exposed.** The function-output cap was 2000, applied with `min()`. So a
binary reporting `total: 50,670` could never deliver more than 2000 of them, whatever
`--limit` the caller passed:

```
before:  --limit 2000 → 2000   --limit 5000 → 2000   --limit 50000 → 2000
after:   --limit 2000 → 2000   --limit 5000 → 5000   --limit 50000 → 50000
         --limit 200000 → 50 670 (truncated: false)
```

The cap is now 100,000 — a guard against an unbounded response rather than a ceiling on
what exists — and hitting it is reported in `warnings` instead of silently shortening the
list. `TestFunctionsRespectsRequestedLimit` pins both directions: a limit below the total
returns exactly that many and marks the result truncated; a limit above it returns
everything and does not.

What this does not claim: 50,670 is an upper bound on plausible entries, not a verified
function count. A leaf function with no prologue and no caller is still missed, and an `E8`
byte inside data can still produce a target. The entries are labelled `x86_call_target` so
they are never confused with symbols.

### The CET prologue bug — the worst defect found this session

A verb sweep across eight fixtures found a plain x86-64 system binary failing **both**
`disasm-native` and `decompile-native`. The cause:

```
$ re disasm-native /tmp/dy --target 0x1040
error: no instructions decoded at 0x1040: decode at 0x1040: invalid x86 instruction
```

The first instruction of `_start` is `F3 0F 1E FA` — `endbr64`, an Intel CET landing pad.
The vendored `x86asm` reports that encoding as `Op(0)` with `Len 1`, and the decoder
rejects `Op(0)` as invalid. **Debian and Ubuntu compile with `-fcf-protection` by default**,
so on any such system the first instruction of most functions failed and disassembly
stopped immediately.

```
before:  disasm ERR, decompile ERR
after:   disasm ok (13 instructions), decompile ok, coverage {decoded: 13, lifted: 13, opaque: 0}
```

`endbr64`/`endbr32` are now recognised before `x86asm` and lifted as `nop`, because that is
what they are on a CPU without CET. Two details cost a cycle each and are worth recording:

- The early return skipped the common tail that fills `Instruction.Bytes`, so the lifter
  received empty data and reported the instruction as opaque *even after* the decoder was
  fixed. Bytes are now set explicitly in that path.
- The bug was invisible from the disassembly surface alone: `functions`, `xrefs-native` and
  `dispatch-native` all succeeded on the same file, because they read the function index
  rather than decoding from a code address.

Nothing about this was architecture-specific in the interesting sense — it was a *default
compiler flag* defeating the decoder for every hardened binary on the system.

### Thumb (T32): detected, decoded, verified

Most real ARM32 code is Thumb, which is a different instruction set over the same bytes.
An odd entry point is the ARM convention for "this code is Thumb"; decoding those bytes as
A32 produces plausible nonsense, so before this batch the engine would have been actively
wrong rather than merely refusing.

Now: `internal/sysimage/thumb.go` decodes Thumb-1 plus the Thumb-2 branch forms, and the
mode is taken **once per image** from the entry point's low bit — never guessed per
instruction. Verified twice, both against `llvm-objdump --triple=thumbv7-none-eabi`:

| Check | Result |
|---|---|
| decoder vs oracle over a whole `.text` (loop, switch, struct, call, `svc`) | **35/35 = 1.000** |
| wiring test through `Disassemble` on a real linked Thumb executable | **11/11** |

```
$ re disasm-native thumb_exe --target 0x20150
0x20150 2 push {r7, lr}
0x20152 2 sub sp, #0x8
0x20154 2 movs r0, #0x2
0x2015c 4 bl 0x2014c
```

That `4`-byte `bl` in a stream of 2-byte instructions is why the walk loop advances by each
instruction's own size rather than a fixed stride — it already did, so Thumb fitted without
restructuring it.

The image also reports `mode: "thumb"` and clears the low bit from the entry address, so
callers see the real start rather than a bit-tagged one.

**A real bug this uncovered.** ARM sets bit 0 on every Thumb code address — including
*ELF symbol values*. Indexing the raw value put functions at odd addresses that cannot be
decoded, and duplicated the even entry-point function. Measured on a real Thumb binary:

```
before:  6 functions, 5 with odd addresses, "main" listed as both 0x20151 and 0x20150
after:   5 functions, 0 odd, correct names
```

The bit is now masked, and its presence is used as *stronger* mode evidence than the entry
point alone, since a symbol table says more than one address does.

**Decompilation declines instead of misfiring.** `liftInstruction` fell through to the
**x86** decoder for any architecture that was not arm64, so ARM bytes were being read as
x86 and every operation came back opaque with a decode error attached — which reads like a
bug rather than "no lifter here". It now declines once, with a reason:

```
structured_declined: "no ARM32/Thumb lifter: instructions are disassembled and typed as
                      opaque, and no structured C is emitted"
coverage: {decoded: 11, lifted: 0, opaque: 11}
```

That distinction — declined versus failed — is the one the brief asks for, and it was
being violated for every non-arm64 architecture.

### Function recovery without metadata

A stripped firmware ELF often has program headers and nothing else. Measured on the real
firehose programmer above: **1 function** before, **1725** after.

The first version of this scanner reported 4089 and looked like a triumph. Measuring what
those addresses actually pointed at is what turned it into something trustworthy:

| Accepted forms | Candidates | Begin like a function |
|---|---|---|
| `BL` + `B` + `B.cond` (first version) | 6522 | — |
| `BL` + `B` | 4088 | **10.9%** |
| `BL` only | 1652 | **54.0%** |
| `B` only | 2553 | **8.4%** |

Two further rules, both measured on the same image:

- **Adjacent pairs.** 91 recovered starts were exactly 4 bytes after another, which would
  make them a single instruction — impossible for an ARM64 function that must return. The
  later of each such pair is dropped, taking 1787 to 1725. An 8-byte gap is left alone,
  because an 8-byte leaf function is normal.
- **A prologue *scan* is a dead end.** Sweeping every aligned prologue-shaped instruction
  found 2609 positions, 1582 of them not reachable by a branch. A narrow frame-record
  signature (`stp x29,x30,[sp,#-N]!`) found only 163 positions, and 4012 of the recovered
  4088 targets do not push a frame record at all — most functions here are leaves. Adding
  a prologue pass would either add 1582 unverified addresses or 87, so neither was built.

So: `B.cond` is never an entry (loop and `if` labels); a plain `B` usually is not either
(8.4% — switch and tail-call targets inside a function); a `BL` is decent evidence (54%).
The rule adopted is **`BL` always, `B` only when the target's first instruction is a
real prologue** (`stp`/`str` with pre-index writeback, `sub sp, sp, #imm`, `paciasp`).
That yields 1787 addresses at 57.5% prologue-like, and drops ~2400 junk entries the
first version would have presented as functions.

Two further corrections:

- **The file was nearly named `scan_arm64.go`.** Go treats a `_arm64` filename suffix as a
  build constraint, so on an amd64 host the package silently lost every symbol in it and
  reported `undefined: scanARM64CallTargets`. It is `scan_calls.go` now, with a comment
  saying why.
- **"54% prologue-like" is not "54% precision".** Leaf functions legitimately start with no
  prologue at all, so the prologue test can only reject, never confirm. The honest claim is
  that the filter removes addresses that are plainly mid-function — not that the rest are
  all correct.
- **x86-64 *was* extended after all — my first measurement was too small.** I rejected an
  `E8 rel32` scan because it recovered 1 of 3 known functions on a 16 KB fixture where
  every call routed through a PLT stub. Re-measured on a real 81.7 MB binary with no
  `.eh_frame`, the same scan finds **79,884 distinct in-range targets**, and the engine
  was recovering **680** functions. See "Large stripped x86-64 binaries" below. The lesson
  is not "heuristics are good" but "a 16 KB fixture is not evidence about an 81 MB
  binary".

The pass only runs when a binary has **no section headers**, so a well-described image
never gets heuristic starts mixed in with real ones. Recovered functions carry source
`arm64_call_target` and are unnamed by construction.

| Swift demangling | verified — `_$s10Foundation…AEvgZ` → `Foundation.CocoaError.Code.fileReadTooLarge.getter : Swift.Bool` |

**PDB identity is validated, not assumed.** A candidate PDB is accepted only if its GUID
and age match the binary's CodeView record. A mismatch is refused and reported:

```
warnings: ["PDB p.pdb does not match the binary (GUID/age differ); not used"]
```

When the binary carries no CodeView record the identity *cannot* be proven, and the
report says `matched: false` with an explicit warning rather than implying verification.

### Primitives and commands

`re callgraph` (72 nodes / 99 edges on `/bin/ls`) · per-section entropy (28 regions) ·
`re demangle` · `re pdb-types` · `re pdb` · `re archives` · `re kernelcache` · PE machine
table.

### Unknown input

Any regular file that no loader claims is **described, not refused**:

```
format           unknown
size             23072 bytes
sha256           008beb6a…ae848cd8
entropy          4.35 (structured)
strings          name=xt-forge, version=0.4.7, codename=Damascus
note             unrecognised format; no disassembly or symbol recovery attempted
```

The SHA-256 covers the whole file even when the preview truncates (a partial hash is
worse than none) and is cross-checked against `sha256sum` and Python's `hashlib`.

## 3. What does not work — read before promising anything

| Gap | Reality |
|---|---|
| **Real Apple containers** | No real dyld shared cache or kernelcache has ever been opened. Both are proven with a *real compiled Mach-O inside a synthetic container*. The DMG was the only container ever validated against a real artifact. |
| **Windows and PowerShell** | `bin/xtforge.cmd` and `install.ps1` were fixed and are verified by **parsing their text only**. No `pwsh`, no usable `cmd.exe` here. They have never executed. |
| **macOS launcher** | The POSIX launcher *was* executed (including a two-link relative chain with a `readlink` shim that rejects `-f`), but never on macOS itself. |
| **Release archives** | Fixed and rebuilt. `scripts/build_release.py` produces per-platform bundles and every one carries a native of the **correct** architecture (verified with `file`: the darwin bundle holds a Mach-O arm64 hub). The Rust core is still host-only — cross-building it needs the target installed — but the script says so instead of silently shipping a Linux binary. The 0.4.6 archives in `dist/` are unchanged and still wrong; rebuild them to fix. |
| **PDB locals and parameter names** | Not read. Signatures give types only; the names live in the symbol stream's `S_LOCAL`/`S_GPROC32` scopes, which are not walked. Typedefs resolve fully and array dimensions render in C order with correct counts (verified against llvm-pdbutil). |
| **`ClassifyAddress`** | Present and tested, called by nothing. |
| **One vendored decoder bug repaired** | The VEX/EVEX truncation panic in `x86asm.decodeAVX` is fixed at source. A recover guard stays around that decoder in case it has others; the guard converts a panic into an error rather than asserting the absence of bugs. |
| **CET landing pads only** | `endbr64`/`endbr32` are handled. Other CET instructions (`rdsspq`, `incsspq`) are not, though they are rare in ordinary code. |
| **`re functions` on stripped ELF** | Functions come from `.eh_frame`, or from branch targets when there is no section table at all; almost none are named, so the table shows `(unnamed)` with a source column. Heuristic entries are labelled `arm64_call_target`, never presented as real symbols. |
| **LZMA DMG chunks** | Explicitly refused. No standard-library decoder exists; needs a vendored one. |
| **`rtti` is ELF/PE only** | Mach-O and other formats refuse through `sources.unsupported()` rather than analysing C++ RTTI. `checksec` now covers Mach-O. |
| **ARM32/Thumb: typed IR everywhere, structured C only for simple functions** | `lift_arm32.go` lifts both (**11/11 instructions, 0 opaque** on a real A32 binary). AAPCS32 is now modelled, so a simple function with `push {r11, lr}` / `bl` / `pop {r11, pc}` emits real C — `static uint32_t sys_callee_200f4(uint32_t arg0, uint32_t arg1) { return (arg1 + arg0); }`. **A real compiled binary still declines**, for two precise reasons listed below. |
| **Thumb only where detected** | Thumb-1 plus Thumb-2 branch forms are decoded; other Thumb-2 wide instructions (load/store multiple, data processing) return opaque. Mode comes from the entry point, so a mixed ARM/Thumb binary decides one mode for the whole image. |
| **Debugger, microcode IR, 70+ architectures** | Not started. x86, x86-64, arm32 (A32), arm64 only. |
| **Android boot payloads** | The header is inventoried and the kernel's first layer is identified, but the kernel is not extracted for disassembly. |
| **UEFI volumes** | Files, GUIDs and types are listed; sections are never decompressed, and **no real firmware image has been tested**. |
| **Android OTA** | Entries and the `payload.bin` header are inventoried; the payload is not extracted, and no real OTA has been tested. |
| **32-bit Mach-O** | Cannot be produced here — `ld64.lld` rejects `-arch i386`. The verifier prints a skip line rather than a half-written lane. |

Also worth stating plainly: **this is not IDA parity.** It is a credible native analyst
toolkit that now covers the load → identify → name → type → navigate path for three
formats. IDA's breadth (70+ processor families) and depth (15+ decompilers, Lumina,
debugger) remain out of reach.

## 7. How this was built, for whoever continues it

Most of the code in this batch series was written by delegated `hy4-flash-free` workers
through the `dsh-opencode-go` provider, one narrow spec per worker: one file, one API,
one acceptance command, in an isolated copy of the module. **Every worker's output was
then re-verified here**, and that step earned its keep repeatedly:

- Three separate tables in this codebase were wrong because they came from memory:
  CodeView leaf kinds (`0x1201` is **ArgList**, not Pointer), Swift `SS`
  (**Substring**, not String), and the archive long-name terminator (`/\n`, not NUL).
  Each was caught by comparing against a real tool, not by re-reading my own spec.
- A worker's own test passed while the behaviour was broken, because the fixture was
  built from the same misunderstanding as the code. Fixtures that drive `ar`,
  `llvm-pdbutil`, `lld-link` or `clang` are worth several hand-built ones.
- Two specs of mine were internally contradictory and the workers flagged it rather
  than silently choosing. Believe them when they do.
- Two workers shipped code with no test file and reported `[no tests to run]` as if it
  were a pass.

The rule that kept this honest: **a check that cannot fail is not a check.** Prefer the
oracle you did not write.
