## 3. Delivered and verified this session

### 3.1 arm64 variable shifts — fixed a real bug, not a flake

Baseline had one failing test. It was **not** a flaky or misplaced test:

```
arm64 variable shift lost operands: Operation{Opcode:"opaque", Raw:"asr w0, w1, w2"}
```

`decodeInstruction` decoded `asr w0, w1, w2` correctly; `liftAArch64` had no case
for variable-shift mnemonics, so it degraded to `opaque`. **Two** real gaps behind
it:

1. `lsl`/`lsr`/`asr`/`ror` with a **register** amount were never dispatched. Only
   the *constant* shift form (a `Scale` field on a shifted-register operand) was
   handled — a genuinely different instruction form.
2. `structured_state.go` required the shift-count register to be `cl`. That is an
   x86-only fact. On arm64 the count register is named in the instruction, so
   every arm64 variable shift was declined *even once lifted*.

Also: shifts must **not** clear flags on arm64 (they do on x86). Both sites were
clearing unconditionally; now scoped by architecture.

**Verified** end to end through the real CLI on a Mach-O fixture:

```
re decompile-native sh.bin --target _asr_var
coverage: decoded 2, lifted 2, opaque 0
opcode: sar ['w0','w1']
structured: uint32_t _asr_var(uint32_t arg0, uint32_t arg1) {
    return ((arg1 & 31u) == 0u ? arg0
            : ((arg0 >> (arg1 & 31u)) | ((0u - (arg0 >> 31u)) << (32u - (arg1 & 31u)))));
}
```

And **behaviourally**: the recovered C compiled next to the original and compared
over 4096 inputs → `arm64 asr matched for 4096 inputs`.

Files: `internal/sysimage/lift_aarch64.go`, `internal/sysimage/structured_state.go`.

### 3.2 Objective-C metadata — new, and it names real code

Naming was the measured weak point (§5.2 of the previous revision: 1 of 200
functions named). New `internal/sysimage/objc.go` (392 lines + 209 test lines)
reads `__objc_classlist` → `class_t` → `class_ro_t` → method lists and names the
code addresses that metadata points at.

On the real DMG app, naming went from **1 to 6** of 200 functions — small in
absolute terms because this app has only five Objective-C methods; on a real
Objective-C binary the same code names far more (10 classes / 10 methods on the
unpacked universal binary's two slices).

The metadata is also exposed as `objc` in `re functions --json`, so a recovered
name can be traced to the structure it came from rather than taken on trust:

```
classes: 5  selectors: 5  named: 5
  -[Delta_Installer.DownloadManager URLSession:downloadTask:didWriteData:...]
  -[Delta_Installer.DownloadManager init]
```

Five format details, each of which cost a debugging cycle and each of which
produced *plausible garbage* rather than an error:

| Detail | Consequence when wrong |
|---|---|
| `__objc_classlist` holds **pointers** to `class_t`, not inline structs | reads fields of unrelated objects |
| `class_ro_t` pointer has **runtime flag bits** in the low three bits | wild address |
| `class_ro_t` starts with four **32-bit** words, so `name` is at +24 and `baseMethods` at +32 | name at +40 gives `"\x01"`; methods at +48 gives nothing |
| `baseMethods` is **one** `method_list_t`, not a null-terminated pointer array | bogus address `0x500000018`, zero methods |
| relative lists store **displacements from each field**, and the selector field points at a **selref slot**, one hop from the string | garbled names on arm64 only — x86_64 uses absolute pointers, so the bug hides unless both slices are tested |

That last one is the reason the arm64 test matters: the x86_64 slice passed
completely while arm64 produced `"\x98\x9d\x04"`. Testing one architecture would
have shipped it.

Also fixed while wiring this up: `re functions --json` silently dropped the
metadata because the hub JSON is assembled field by field — adding a field to the
Go struct is not enough if nothing emits it. Caught by checking the CLI output
instead of the test result.

### 3.4 DMG / UDIF container — new capability

New package `internal/udif` (504 lines + 364 test lines). Parses Apple disk images
**in process**, with no `hdiutil` (does not exist on Linux) and no `7z` shell-out,
keeping the "no external tool" property the rest of SYS holds.

What it does:
- Reads the `koly` trailer (last 512 bytes) for chunk-table location and data fork.
- Walks the XML property list **as tokens**. A plist is key/value *siblings*, so
  Go struct tags cannot describe it — this was the first bug: `<key>Attributes</key>`
  and its `<string>` are separate children of the same `<dict>`.
- Decodes `mish` chunk tables and decompresses `raw`, `zero`, `zlib`, `adc`, and
  **`lzfse`** chunks. `bzip2` and `lzma` decline with an explicit message.
- Reconstructs a partition to exact byte length, zero-filling sparse ranges.
- Probes the result for `hfs+`/`hfsx`/`apfs`.

Two bugs found and fixed while building it, both of which would have produced
silently wrong output:
- **plist `<data>` is base64 text.** Unmarshalling straight into `[]byte` keeps the
  literal characters, so chunk tables decoded as `"bWlzaA=="` instead of `"mish"`.
- **Chunk types with no decoder must fail loudly**, not produce zeroes that look
  like a sparse region. There is a test for exactly that.

Vendored `internal/thirdparty/lzfse` (1077 lines, Unlicense/public domain) with a
provenance README, matching the existing `thirdparty/xarch` convention.

**Verified against a real DMG** (`delta.dmg`, UDIF v4, LZFSE, 4 562 200 bytes):

```
version=4 partitions=8 compressed=4543748 uncompressed=41418752
methods: map[ignore:3 lzfse:13]
[4] "disk image (Apple_APFS : 4)" sectors=80816 written=41377792 chunks=9
extracted partition 4: 41377792 bytes, fs="apfs"
```

**And by independent cross-check** — the check that actually matters. 7z recovered
`.VolumeIcon.icns` from the same DMG through its own APFS reader; those bytes
appear verbatim inside the partition this package reconstructed:

```
verified 3584 reference bytes at partition offset 700928
```

Without that, "extraction succeeded" would only prove the right *number* of
bytes, not the right bytes.

### 3.5 DWARF import — exact names and sizes when debug info survives

New `internal/sysimage/dwarf.go` reads `DW_TAG_subprogram` entries through the
standard library's per-format `DWARF()` accessors (ELF, Mach-O, PE) and names the
addresses they describe. Using the accessors rather than assembling sections by
hand matters: they handle DWARF version differences and compressed sections, and
hand-rolling that is how off-by-one decoding bugs get in.

Same rule as everywhere else here — DWARF **names** addresses, it never invents
functions. A stale or bogus entry produces nothing instead of a phantom function.

Verified on a `clang -O1 -g` build where the true sizes are known:

```
compute_total  0x1120  size=8
main           0x1128  size=6
```

**The bug worth recording:** `DW_AT_high_pc` decodes to `uint64` when its form
class is *address* and to `int64` when it is a *constant offset*. Handling only
`uint64` left the value at zero, so sizes came out as `0x1120 - 0` and printed as
**negative** — `size=-4384`. A wrong-by-4-billion number is much easier to notice
than a subtly wrong one, which is the only reason it was caught immediately.

### 3.6 DMG as a container in SYS

`internal/sysimage/container_dmg.go` (302 lines) bridges disk image → Mach-O:

- Detects UDIF by the **`koly` trailer**, not the extension (people rename `.dmg`
  to `.img` constantly).
- Extracts the filesystem partition, scans for a Mach-O that **validates
  completely** — header, every load command fits and advances, segment extents
  consistent. Random bytes do not satisfy that, which is what makes a scan safe.
- Reports `format: dmg` and bounds in-memory expansion at 512 MiB with a clear
  message rather than an OOM.

**Verified** through the real CLI:

```
re overview delta.dmg  → format: dmg, member: offset:0x2c2000, arch: [x86_64]
re functions delta.dmg → 200 functions recovered
```

The IPA path is unchanged; `TestMachOverviewAndIPAMember` still passes.

A subtle bug fixed here: `inspect()` overwrites `Format` with the *payload's*
format, so the container label was being clobbered. The container name is now
captured before `inspect()` and reapplied after.

**A design rule needed correcting, and the measurement is what caught it.** I had

declaring its own entry points**, the PE equivalent of ELF's exported `dynsym`
entries, so it may add function starts. Reconstructed metadata — Objective-C method
pointers, DWARF rows — still may not. Both behaviours are now stated separately in
the code.

shipped 0.4.6 artifacts:

```

xt-forge-0.4.6-windows-x86_64.zip:  missing native executable
```

confirmed independently by listing them: the Darwin tarball has 541 entries and no

tarball carries both `xtforge-native` and `xtforge-hub`. So macOS and Windows users get
a Python-only payload while the README advertises native executables.

The test is `@unittest.expectedFailure`, not skipped — deliberately. It keeps the suite

test starts passing and unittest reports *unexpected success*, which is the signal to
remove the decorator. A skip would have rotted silently.

The invariant test is the one worth keeping honest. It asserts the negative that all the
comments claim: Objective-C method pointers and DWARF rows must name existing functions
and never add starts, while PE exports legitimately may. Those four tests are the only
thing preventing a future change from quietly turning "names" into "invents code".

`SSG -> Box<Swift.String>`. The worker noticed the conflict, followed the *test*, and
said so. The test was the wrong half: `Ss` is String and `SS` is Substring in the Swift
ABI. Corrected in both the table and the test, so the two primitives no longer collapse
to one name. Two workers in this session have now caught inconsistencies I wrote.

### 3.18 Thirteenth batch — PDB aggregate layouts

The last piece of the PDB type story: struct and union layouts. Without it a struct
parameter rendered as `type(0xNNNN)`; with it the signature reads as C.

```
$ re pdb-types r.pdb
10 type records (ArgList:3, FieldList:1, Pointer:1, Procedure:3, Structure:2)
struct Point (int, int)
int (struct Point *, struct Point)
int (void)

1 aggregate layouts
struct Point /* 8 bytes */ { int x; int y }
```

| File | Change |
|---|---|
| `internal/sysimage/pdb_signatures.go` | `ReadPDBAggregates` — `LF_STRUCTURE`/`LF_UNION`/`LF_FIELDLIST`/`LF_MEMBER`; `pdbTypeName` renders `struct Name` |
| `cmd/xtforge-hub/main.go` | `re pdb-types` carries `aggregates` |
| `xtforge/cli/scan_cmd.py` | human output lists layouts |

Details that matter and are now enforced by tests:

- **Field offsets are byte offsets, not declaration order.** `struct Pair { char tag;
  long long value; }` puts `value` at **8**, not 1, and the test asserts the aligned
  offset rather than the obvious one.
- **The offset is a NumericLeaf** — `u16` below `0x8000`, a `u32` otherwise. Reading it
  as always-`u16` would silently misplace any struct field past 32 KiB.
- **`LF_UNION` stores its size as `u32`, `LF_STRUCTURE` as `u16`.** One field, two
  widths; treating them alike shifts every subsequent read by two bytes.
- **Forward declarations are dropped.** The same struct appears twice — once as a
  `forward ref` with `sizeof 0` and no fields, once as the definition. Emitting both
  would double every struct in a report.
- **`<unnamed-tag>` is filtered.** Anonymous aggregates would otherwise look like a
  type named "<unnamed-tag>".

Verified against `llvm-pdbutil dump -types`: member names, types and offsets agree, and
the test reports `compared 2 members with llvm-pdbutil`. It compares *offsets*, not just
names, because a decoder that ignores padding produces the right field list at the wrong
addresses.
